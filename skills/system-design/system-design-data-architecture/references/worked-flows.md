# Worked Critical Flows

These compact scenarios are synthetic teaching assumptions, not deployed-system evidence. They illustrate the contract, not universal infrastructure prescriptions. Use the linked production case packs for full workload, assumptions, constraints, recovery, and acceptance details rather than duplicating their case data.

## Payment/order: commit succeeds, acknowledgment is lost

`FLOW-PAY-01` (synthetic trace record; IDs below are local design-record examples, not claims of repository artifacts): `REQ-PAY-01` — checkout retries for one accepted business operation must not create a second capture or ledger effect; user-visible unknown outcome remains pending/queryable. `HLD-PAY-01` — checkout/API owns operation acceptance and stable operation identity; the processor is an external capture authority, while the ledger owns local financial entries. `CMP-PAY-01` — checkout API, operation record, processor boundary, webhook inbox, ledger, reconciler/status reader. `LLD-PAY-01` — persist operation ID and payload hash before processor call; reuse that identity on retry and pass a stable processor idempotency key when supported; deduplicate provider event IDs; report `PENDING` after uncertain outcome until status/webhook/reconciliation resolves it. If provider idempotency is unavailable, do not blindly repeat capture while the first outcome is unknown; disambiguate first. `VER-PAY-01` — force processor commit with lost acknowledgment, replay the same business operation and webhook under the stated provider-idempotency/reconciliation policy, then observe exactly one capture/effect and a queryable pending result until resolution. Checkout supplies the stable business-operation ID and payload; the scenario does not claim identical response bodies for all APIs. A sequence clarifies the timeout/retry race; dataflow is optional if the contract is clear. See [production case 1: Payment Timeout and Duplicate Webhook](../../system-design-case-catalog/references/production-case-packs.md#1-payment-timeout-and-duplicate-webhook).

## CDC plus backfill: stale backfill races newer search data

`FLOW-SEARCH-01` (synthetic trace record; IDs are local design-record examples): `REQ-SEARCH-01` — indexed search is derived from committed source records and cutover must not expose an unverified migration; users must not see a stale overwrite as current. `HLD-SEARCH-01` — source database remains authoritative; index is rebuildable/derived; reads switch only after parity and lag gates. `CMP-SEARCH-01` — source database/log, CDC consumer, resumable backfill, version-fenced index writer, query service, parity/lag checker, read-switch flag. `LLD-SEARCH-01` — attach source version/LSN to each CDC and backfill update; atomically apply only when newer than the indexed version; checkpoint backfill; stop on failed parity/lag gate and keep source reads. `VER-SEARCH-01` — commit source version 5 through CDC, then inject delayed backfill version 4; observe index version remains 5, source read path remains selected, and cutover is blocked if the declared parity/lag gate is unmet. The source is authoritative; if checkpoints restart or lag grows, throttle/stop, reconcile and replay before switching. The dataflow view is optional; sequence/state are separate if cutover order or migration lifecycle is the question. See [production case 7: Live Database and Search Migration](../../system-design-case-catalog/references/production-case-packs.md#7-live-database-and-search-migration).

## Mobile local edit: logout, conflict, and deletion

`FLOW-CLIENT-01` (synthetic trace record and explicit example policy; none of these choices is universal): `REQ-CLIENT-01` — offline edits for one account must not cross accounts, overwrite a concurrent edit silently, or resurrect a deleted record; user sees pending, conflict, or deleted/rejected outcome. `HLD-CLIENT-01` — server owns shared record and deletion state; local queued edits are account-bound derived state; deletion wins over stale offline edits. `CMP-CLIENT-01` — authenticated sync endpoint, record owner, deletion/tombstone state, versioned record, account-local pending queue and UI. `LLD-CLIENT-01` — record IDs are never reused and the owner retains a deletion marker for each deleted identity; tombstone delivery to clients may be delayed. In one atomic owner-side operation, re-check current account/record authorization, reject a deleted identity, compare submitted base version with current version, and apply/increment only if all predicates hold. A tombstoned identity returns `410 DELETED` without mutation; a live-record version mismatch returns `409 VERSION_CONFLICT` with current version, never auto-overwrites. Synthetic logout policy: erase that account's pending payload locally at logout; never transfer/replay it under the next account. On `409`, client moves pending edit to visible conflict and requires explicit reload/re-entry; on `410`, it discards the pending edit, removes the local copy when tombstone arrives, and shows “This record was deleted; your edit was not applied.” `VER-CLIENT-01` — queue base-version-4 edit, disconnect, delete server record at version 5, reconnect and send edit before tombstone delivery; observe atomic `410`, unchanged deleted server state, then local deleted state on tombstone, with no resurrection. Separately logout with a pending edit and sign in as another account; observe no queued payload is sent. The policy deliberately trades automatic edit preservation for account isolation and deletion safety in this synthetic case. A state view clarifies lifecycle; use sequence only if sync ordering needs explanation.
