# Portable operating contract

**Purpose:** Execute bounded work safely and produce behavior-based evidence in any authorized project, whether or not AGS, OMP, or Paseo is present. This contract is advisory; it does not create host enforcement.

## Keep four kinds of context separate

| Kind | Contents | Source of truth |
| --- | --- | --- |
| Stable/shared contract | Ownership, approval, account/data boundaries, evidence and review rules | This document; update through its owner |
| Project facts | Repository, stack, commands, fixtures, allowed data, eligible profiles, evidence location | The enrolled project's `project-contract.md` or authoritative local instructions |
| Reusable procedures | Skill/workflow bodies and tool-specific operating recipes | Available AGS lookup, installed guidance files, native runtime skills, or existing project docs; load when relevant |
| Active state | Current task, revision, attempts, decisions, blockers, receipts | Explicit task brief/card and task-local report; never silently promote to stable guidance |

AGS is optional. Use the available authorized route: AGS MCP body lookup; installed skill files; native runtime skills; existing project documentation/code examples; or a complete explicit brief. A catalog listing is not a loaded body, and consultation is not proof of adherence. Do not auto-install AGS. OMP and Paseo are optional adapters, not prerequisites for the contract.

## Before dispatch

1. Confirm human authorization for the exact project, account/domain, task, files, data, runtime actions, profile, and evidence destination. A workspace/worktree or profile name does not prove eligibility or isolation.
2. Read the project's real instruction entry points. Identify an owner for each write and a separate eligible reviewer. Do not cross account boundaries with source, journals, credentials, or private evidence.
3. Load relevant standards through whatever approved route exists. If standards lookup is absent, use authoritative project guidance, native skills, and the explicit brief; record the route and unknowns without claiming AGS use.
4. Discover missing commands, conventions, environment prerequisites, fixtures, or expected behavior before implementation. Do not guess a verification lane. Stop if a launch-critical fact remains unavailable.
5. Freeze the task's goal, exact owned paths, consumer-visible acceptance criteria, executable checks, safe data, exclusions, and stop/escalation conditions. Baseline and treatment keep mandatory standards, profile/model/settings, and independent review constant wherever authorized; describe only their intended process difference.

## Execution and evidence

- Change only the approved scope. Instructions and worktree placement are not filesystem, network, credential, or database containment. Tool-approval prompts are not proof of effective host policy.
- Verify the changed behavior through the real project surface and an approved isolated fixture. A passing build/test alone is not proof of consumer-visible behavior. Do not weaken an acceptance criterion when its prerequisite fails.
- Bind results to the source revision and relevant local state; list exact commands/scenarios, observable output, failed/blocked attempts, repairs, and independent-review status. A material repair invalidates affected evidence; re-exercise it and request a fresh independent review.
- Keep raw journals and other private inputs local. Share only authorized sanitized summaries. Use existing counters only within their explicit inventory and scope.
- Report each measure independently: reported zero is `0`; absent is `unknown`; inapplicable is `N/A`. Unknown cost, usage, consultation, or coverage is not zero, savings, or success. Estimates are not invoices. Name denominators and retain failed, retried, blocked, and not-started attempts.

## Authority and lifecycle

Only the project owner grants enrollment, profile eligibility, budget, phase approval, adoption, or activation. A plan/G1 approval does not approve G2 task execution or G3 adoption. The implementer cannot self-approve or replace an independent verdict. Human approval does not prove a control is enforced. Stop for unresolved authorization, account, sensitive-data, migration, production, or safety questions; return evidence and the exact decision needed. No automatic fallback to another account, premium route, merge, release, or deployment.

Task-specific exceptions never expand scope silently. Preserve source/runtime failures and measurement limits in the local handoff. This contract is guidance, not a runtime gate.
