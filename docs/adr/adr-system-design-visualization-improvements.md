# ADR: One semantic graph, safe derived viewing, and evidence-based N+1 verification

Status: human-approved baseline and correction delta; Subagent-Driven implementation and focused baseline repair authorized on 2026-11-05. Date: 2026-11-05. Decision owner: requesting maintainer; technical owner: registry maintainer. Baseline approval: explicit “Approve technical design,” including trace compatibility; Personal review domain authorized; explicit execution approval: “approve corrections; subagent-driven; repair baseline.” Source: [approved PRD](../prd/prd-system-design-visualization-improvements.md). Scope: visualization A and N+1 B1 only.

## Context

The current JSON → draw.io pipeline already has eight diagram types, evidence/confidence, metric provenance and optional multi-view manifests. Upstream stack-diagram contributes presentation ideas, not a semantic renderer. Replacing our pipeline would lose established editing and evidence contracts. Local draw.io Desktop exported an existing context fixture successfully, but the inspected image still has crowded text and hard-to-see connectors. Baseline export availability does not establish dark-theme or offline-package correctness.

N+1 remedies already exist in database, ORM and GraphQL guidance. Missing explicit design/review integration and runtime query-growth evidence are the relevant gaps. A temporary Python/SQLite experiment demonstrated equal synthetic results with SELECT counts 2/11/51 for per-parent loading versus 2/2/2 for a bounded single page; this is not ORM or PostgreSQL evidence.

## Decision

1. **Preserve semantic ownership.** JSON remains authority; draw.io is generated editable presentation; images and HTML are derived copies. Add optional theme presentation parameters, not a second graph or arbitrary HTML editor. Keep existing IDs, metric/evidence meaning, manual-edit protection and manifest checks.
2. **Keep one renderer.** Extend existing label/geometry planning and style surfaces, including sequence and ERD paths. Add a per-render palette with light as the backward-compatible default; never mutate the shared catalog globally. Strict geometry uses complete planned text bounds; visual inspection remains independent.
3. **Package PNG, not executable SVG/HTML.** A new local `export_html.py` orchestration surface validates the spec, generates/stages light/dark draw.io outputs through existing gates, exports PNGs, and emits one static HTML with embedded PNG data and escaped metadata. No scripts, external resources, raw SVG or spec-provided markup are inserted. Generated text runs escape spec-origin text before internal renderer formatting. Preserve existing output on failure and refuse conflicting final paths by default. The detailed interface and error contract belongs to [the SRS](../srs/srs-system-design-visualization-improvements.md#lld-002--derived-local-package).
4. **Use a real, minimal local N+1 example.** Select Python stdlib SQLite with instrumented emitted statements and a paginated relation read. This has no service/account/package dependency. It demonstrates framework-neutral query shape; applicable ORM/GraphQL behavior is evaluated separately using existing guidance. Do not infer PostgreSQL latency, ORM efficacy, cross-framework correctness or production capacity from SQLite.
5. **Preserve approved IDs; align trace validator and parser.** D-TRACE is resolved in implementation following explicit maintainer direction (“Align trace parser too”) after an actual required-scope failure. Approved source IDs are retained without modification. The grammar in both outcome validation and document-trace parsing accepts single uppercase-alphanumeric namespaces (`BRD-*` and `REQ-*` with >=3 digits, `AC-*` with >=2 digits) alongside legacy numbers, with authority-scoped declarations and references. Scoped trace alignment is independently reviewed and closed (reviewer `4811d741`, notification `a2030859`). Do not silently migrate IDs, add aliases or empty machine trace arrays.
6. **Keep publication and spend separate.** No public gallery, automatic asset download, package installation, live model execution, deployment or release is authorized. Actual execution routes and quotas are resolved at the separately gated implementation/evaluation entrypoints.

## Alternatives considered

- **Adopt upstream authored HTML as authority:** rejected; incompatible semantic/editability and provenance model, manually authored geometry and untrusted-markup concerns.
- **Write a second native HTML/SVG graph renderer:** rejected; duplicates layout and semantic projection without an approved need. Static PNG viewing trades interactivity/vector zoom for a smaller, safer contract.
- **Require a PostgreSQL/ORM service for the first demonstration:** not selected; installed binaries exist but no ready app/driver/harness was established. SQLite exercises the selected pattern without installing or starting a service. A later adapter-specific hypothesis may justify a different runtime without replacing this proof.
- **Force every N+1 fix into one JOIN:** rejected; row multiplication, hydration cost and pagination/result equivalence matter alongside statement count.
- **Renumber approved requirements or special-case this slug:** rejected; it would orphan approval links or encode an incidental input exception. A generic bounded grammar is the proposed compatibility mechanism.

## Consequences and approval boundary

Static HTML can be viewed offline without maintaining a new renderer, but is a derived snapshot, not an editor. Theme/layout changes must preserve all diagram paths, not only ordinary edges. Conservative text planning cannot certify actual font/export readability. Query-count evidence must be paired with results and resource observations; fewer queries do not guarantee lower latency.

## Reversal

Before publication, return to the previous verified canonical skill/tool revision and regenerate outputs; keep existing JSON and legacy light outputs valid. New HTML outputs can be discarded without changing source evidence or approved IDs. Do not enable namespaced-ID output in additional producers until validator compatibility is deployed and checked; if that compatibility cannot be accepted, retain the trace audit as an owned blocker rather than rewrite approved history.
