## Proposed synthetic coverage payload example

**NOT RUN; illustrative fixture, not measured usage.** This is a `usage.lineage` payload projection, not a complete ingestion envelope. All fixture records share domain `d1`, project `p1`, task `t1`, run `r1`, attempt 1, counter scope `billing1`, epoch `e1`, compatible disjoint input semantics and qualified native protocol `fixture-v1`. Define `R(id)` as the typed event reference `{domain_id:"d1",project_id:"p1",source_instance_id:"s1",source_event_id:id,event_revision:1}`. Native request unit IDs `u1`, `u2`, `u3` are independent of collector and actor. Synthetic registry authority maps `R("decl")` to native membership/completeness evidence; the typed declaration alone is not its own authorization.

Parent summary S has `input_tokens:30`, `aggregation_role:"inclusive_summary"` and this closed lineage object, with `R(...)` notation expanded before any actual JSON encoding:

```text
{
  usage_unit_id: null, counter_scope_id: "billing1", counter_epoch: "e1",
  interval: {start_sequence: 1, end_sequence: 3},
  covered_units: [
    {usage_unit_id: "u1", event_ref: R("c1")},
    {usage_unit_id: "u2", event_ref: R("c2")}
  ],
  membership: "exhaustive", value_coverage: "complete",
  request_coverage: "complete", declaration_authority: "native_harness",
  declaration_ref: R("decl"), semantics_version: "fixture-v1"
}
```

| Fixture record                   | Canonical unit / interval | Value           | Closed lineage specialization relative to S                                                                               |
| -------------------------------- | ------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Child C1 at R("c1")              | u1 / [1,2)                | 10 input tokens | `usage_unit_id:u1`, interval [1,2), covered_units exactly u1/R("c1"); all complete/exhaustive under qualified declaration |
| Child C2 at R("c2")              | u2 / [2,3)                | 20 input tokens | `usage_unit_id:u2`, interval [2,3), covered_units exactly u2/R("c2"); all complete/exhaustive under qualified declaration |
| Distinct parent call P at R("p") | u3 / [3,4)                | 5 input tokens  | `usage_unit_id:u3`, interval [3,4), covered_units exactly u3/R("p"); same authority proves disjoint membership from u1/u2 |

Leaves use `aggregation_role:"exclusive_leaf"` and their own typed refs; all other lineage keys are exactly those shown in S. Expected mathematical total: choose complete leaves 10+20 for S's exhaustive covered set, then add distinct P=5 → **35**. Or, if qualified S is complete but child detail is partial/missing, choose S=30 and P=5 → **35** with incomplete request detail. Never S+C1+C2+P=65. No rates are supplied, so cost remains unknown. A partial membership declaration or unverified overlap between P and S withholds the affected full total, not an optimistic 35. Copying C1 via collector B changes receipt metadata only; an equivalent second source must map to u1 with approved equivalence evidence or overlap remains unknown. Correcting C1 to revision 2 requires qualified summary reconciliation/new lineage revision before request completeness can be reasserted.
