# Review Feedback Log: Scout 4A HLD Review

Traceability mapping connecting real reviewer feedback comments from the Scout 4A architecture document review to the rules enforced by `system-design-document`.

| # | Feedback Finding | Reviewer Comment / Issue Observed | Standard Rule | Rule Name & Required Correction |
| :-: | :--- | :--- | :-: | :--- |
| **1** | Open items kept after resolving | Questions answered during the review cycle remained listed in the "Open Questions" section, confusing the client PO about whether architectural choices were settled. | **Rule 1** | **Resolved items leave the list**: Once an open question is answered, it must leave open items and move into Decisions with cited evidence. Open items / Sign-offs keeps only pending agreements as "Agree that..." rows, never questions. |
| **2** | "my call" owners | The Decisions table listed "my call", "AI", or unspecified roles in the "Made by" column rather than identifying recognized stakeholder parties. | **Rule 2** | **Declared decision owners**: "Made by" column uses only declared parties (`Vendor`, `Client technical team`, `Client product owner team`). Credit Client only if decided in discussion; pending choices live in sign-offs. |
| **3** | Arrows into Mixpanel | In dataflow diagrams, arrows were drawn pointing from the sync job into Mixpanel, incorrectly implying the sync job writes to Mixpanel when it only extracts analytics data. | **Rule 3** | **Data movement arrows**: Arrows represent the direction of data flow (`source -> job -> staging -> store`), never "who queries" or "who reads". No arrow may point into a system that the design only reads from. |
| **4** | HLD too busy | The architecture diagram displayed over 25 tightly packed components, cross-cutting connections, and mixed abstraction levels on a single canvas, overwhelming reviewers. | **Rule 4** | **Top-to-bottom HLD**: Clean top-to-bottom hierarchy: users -> frontend -> backend (cross-cutting identity in front of business modules, then stores) -> outside systems along the bottom. Maximum ~15 boxes; detailed subsystems move to separate diagrams. |
| **5** | Schedule mixed five jobs + Auth/RBAC duplicated | A catch-all "Schedule" module combined five unrelated background tasks, while Authentication and RBAC boxes were redundantly duplicated inside each individual service box. | **Rule 5** | **Module boundaries & single identity**: One module per capability; no catch-alls ("Schedule", "Common", "Manager"). Authentication and authorization form ONE identity & access layer drawn once in front of all business modules. Include 1:1 screen-to-module mapping. |
| **6** | Options hard to compare | Data ingestion options were presented with mismatched diagram shapes, differing evaluation rows, and no clear separation between repo-verified facts and assumptions. | **Rule 6** | **Solution options parity**: Each option gets its own small diagram with the same shape (`sources -> job -> staging -> store`), a short note, and one unified comparison table sharing identical rows. Recommended option first; fallbacks in order with rationale; explicit verified vs assumed evidence list. |
| **7** | Word tables broken | Exported `.docx` files had clipped text, overflowing table columns, missing borders, and broken layouts across page breaks when opened by executive reviewers. | **Rule 9** | **Export integrity (docx/pdf)**: Tables require explicit borders, fixed layout (`w:tblLayout w:type="fixed"`), column widths fitting longest words, repeat header row (`w:tblHeader`), and row split prevention (`w:cantSplit`). Visual inspection before delivery. |
