# Caller-selection qualification protocol

Exact execution configuration/resource grant is still pending. No model-selection efficacy, AC15 acceptance or whole-plan qualification is claimed by this document.

## Boundary under test

Two different claims require two different evidence lanes:

1. Registry retrieval: an actual `load_skills_for_keywords` call with `keywords: ["flutter cicd"]` returns the intended skill and required composites through the real index. Separate input elements `["flutter", "cicd"]` are not implicitly joined. These deterministic integration tests do not prove caller interpretation.
2. Caller association: a model receiving the raw request chooses an associated concept only when that work is actually requested, then makes the real tool call. Parent-authored normalization fixtures or a generated JSON answer are not evidence of an actual selected tool argument. Text-only intended arguments may be scored separately, explicitly as transcript evidence.

Neither claim proves universal semantic recognition, safe execution, or full T3/T4 workflow qualification. Selection never grants action authority.

## Pre-run frozen inputs

Before any authorized caller trial, seal the following exact bytes/configuration in the existing pilot evidence directory:

- This protocol revision, case inputs, context, expected classification and grading rules; keep expected labels outside worker access.
- Current/candidate caller-instruction bundles, catalog entries/keyword metadata and relevant tool descriptions, with ordered allowlisted paths, hashes, byte counts and original source identity. T0's earlier skill-only snapshot is not silently treated as a snapshot of later tool/index-description changes.
- Same skill identities/catalog extent, host capabilities, permission policy, task input and allowed discovery in both arms. Any catalog keyword difference is explicit and bounded to the proposed change; do not hand-pick extra hints for the candidate.
- Actual eligible provider/model/effort, supported host mechanism for actual tool-call capture, approval actor/reference/scope/expiry, slot/attempt/concurrency/spend limits, arm order/repetitions and invalidity/replacement policy.
- A separate blinded reviewer/validator with the expected target association. The model receives request, necessary context, available catalog/tool instructions, and no expected concept or example that discloses the held-out case answer.

No new paid run is implicitly added to the original 144-trial budget. Operator approval determines whether these cases are a separately scoped selector experiment or allocated into a revised complete trial contract; neither occurs automatically.

## Actual evidence and grading

Retain immutable per-attempt raw request/context, delivered instruction/catalog identities, actual configuration, arm/order, every observed selection call with unmodified arguments/results and timestamps, final response, clarification/abstention, failure classification and usage provenance. Delivered resources and actually loaded resources are separate fields.

- Include case: the caller must select the single associated concept `flutter cicd` in an actual tool call. Missing selection, only split tokens, a refused/missing tool call, or a tool error is not a successful retrieval. Distinguish interpretation failure from infrastructure failure.
- Exclude case: no actual selection may manufacture Flutter CI/CD as requested work; quoting or discussing those words alone is not a selection. Preserve all calls, not just the final corrected one, so an unsafe/irrelevant first selection cannot disappear.
- Unresolved case: report whether the caller abstained/requested the needed association or invented it. Do not inflate specificity by counting all abstentions as true negatives.
- Report target-concept false positives (extra Flutter CI/CD concept) and false negatives (missing associated concept), per-case outcomes and target precision/recall/specificity where denominators exist. Do not claim correctness for ungraded other skills or the entire catalog.
- An incomplete/timed-out task remains in the attempt inventory; it is not quietly removed from success accounting. Missing/truncated real call evidence is unknown/infrastructure-invalid coverage, not a pass or proof that the caller selected nothing.
- Blinded independent adjudication resolves context-dependent disputes without changing expected labels after seeing arm results; contested labels pause promotion and require a versioned pre-outcome contract revision for any new run.

Predeclare required observation coverage: actual emitted selection calls and their arguments/results must be captured. On-demand references intentionally unopened under the shared discovery rules are not missing loads. If an actual required load/call lacks capture, the corresponding claim is not qualified.

## Admission and promotion

No execution with a missing eligible profile/resource grant or missing real-call capture mechanism. No host controls may be weakened to enable the experiment. Retain all failures and honest unknown usage. Apply approved thresholds only; observed finite success is not proof of universal caller behavior.

Caller-selection evidence can qualify only the explicitly approved normalized input boundary. Full workflow/safety efficacy and generated distribution remain subject to the original T3/T4/T5 gates unless the operator separately approves a changed scope without converting unperformed checks into PASS.
