This is the classic N+1 query pattern: one query loads the orders, then one product query runs for each order. The first step is to measure it in production-like conditions, including query count, latency, returned row counts, database CPU, and whether the product relationship is one-to-one or one-to-many.

Replace the per-order lookup with a set-based operation. For example, load the orders, collect the distinct product IDs, fetch all required products with a single `WHERE id IN (...)` query, and index them by ID in application memory. If the database relationship is suitable, use a join or ORM eager-loading/include facility that generates an efficient join or batched query. A join must still preserve the intended order/product cardinality and avoid duplicating large order fields unnecessarily.

Keep the response contract unchanged, select only the columns needed by the endpoint, and paginate orders rather than loading an unbounded history. Verify that the product key and filtering columns have appropriate indexes, and inspect the query plan rather than adding indexes speculatively. If product data is shared across many requests and changes infrequently, a bounded, invalidation-aware cache may help, but it should complement—not hide—an inefficient query pattern.

Validate the change with query-count assertions and benchmarks covering empty results, duplicate product IDs, large pages, missing products, and realistic database latency. Compare p50/p95 latency, database load, memory use, and correctness before and after. A successful fix should reduce the number of product queries from roughly one per order to a constant number per page while maintaining acceptable response size and authorization boundaries.
