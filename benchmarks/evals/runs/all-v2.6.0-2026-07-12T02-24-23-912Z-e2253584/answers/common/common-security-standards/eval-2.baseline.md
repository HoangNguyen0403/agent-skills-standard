First classify the PII by sensitivity, retention needs, search requirements, and regulatory obligations. Encrypting selected fields can reduce exposure from a database dump, but it does not replace access control, TLS, least privilege, backups protection, or application security.

Use authenticated encryption from a vetted library, such as AES-256-GCM or an approved modern equivalent. Generate a unique, unpredictable nonce/IV for every encryption operation; never reuse a nonce with the same key. Include the record identifier, field name, schema version, or tenant context as authenticated associated data when appropriate, so ciphertext cannot be moved between contexts unnoticed. Store the nonce, ciphertext, authentication tag, and key-version metadata in a well-defined format. Treat authentication-tag failures as security errors and never silently return corrupted or unauthenticated plaintext.

Manage keys separately from the database, preferably with a cloud KMS or HSM. Use envelope encryption: a KMS-protected key-encryption key wraps one or more data-encryption keys. Restrict decrypt permission to the smallest service role, audit key use, rotate keys on a documented schedule, retain old key versions long enough to decrypt existing records, and define a re-encryption and emergency-revocation procedure. Do not put keys in source code, ordinary environment files, logs, backups, or the same unprotected database export as the ciphertext.

Encrypt data in transit with current TLS and protect backups, replicas, exports, caches, and logs as carefully as the primary table. Minimize collection, redact responses and logs, enforce row- and field-level authorization before decryption, and avoid broad bulk-decryption endpoints. Test restore and key-rotation procedures, access-denial paths, and incident response. If exact-match lookup is required, use a separately protected keyed hash/blind index where suitable; do not use deterministic encryption or raw hashes without analyzing its leakage and password-like data risks.
