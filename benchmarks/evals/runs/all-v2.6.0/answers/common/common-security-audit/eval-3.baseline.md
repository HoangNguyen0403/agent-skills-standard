IDOR (insecure direct object reference), commonly called broken object-level authorization, occurs when an API accepts an object identifier from a caller but does not verify that the authenticated caller is allowed to access or change that specific object. It is an authorization defect, not merely an issue with predictable numeric IDs; random UUIDs reduce enumeration but do not replace authorization.

Build an object authorization matrix first: for each endpoint and HTTP method, record the object type, identifier source, required role/tenant, allowed actions, and expected behavior for owner, same-tenant non-owner, different-tenant user, admin, anonymous, and deleted/disabled accounts. Include nested resources, bulk endpoints, exports, search/filter parameters, GraphQL fields, downloads, websocket messages, and background-job status or cancellation endpoints.

Test with at least two ordinary accounts from different tenants plus any relevant admin or service roles. Capture an object owned by account A, then replay requests as account B while changing every identifier in the path, query, body, headers, and batch items. Test read, update, delete, share, restore, download, and metadata actions, including alternate methods, pagination, sorting, filtering, and guessed or copied identifiers. Also test horizontal access (peer users), vertical access (ordinary user versus admin-only object), and tenant-boundary access. A denial must be enforced server-side and should use a consistent 403/404 policy that does not leak existence.

For each finding, preserve a minimal reproducible request/response pair, the two identities and object ownership, endpoint, impact, and whether the action reads or mutates data. Verify that authorization is checked after resolving the object and before serialization or side effects; avoid trusting client-provided owner, tenant, or role fields. Centralize policy checks where practical, but still test endpoint-specific behavior. Database queries should constrain by both object ID and authorized principal/tenant where possible, and bulk operations must authorize every item rather than only the first.

Add automated authorization tests to the API test suite and run them in staging with production-like policies. Use property-based or generated identifier tests where useful, and supplement them with DAST/manual testing because scanners commonly miss business rules. Log denied authorization attempts without sensitive data, alert on unusual cross-tenant probing, rate-limit enumeration, and review caches so an authorized response cannot be served to another user. Fix by enforcing object-level policy on every read and write, then re-test neighboring endpoints and all alternate access paths before release.
