Before go-live, perform a threat-driven review of the Node.js service, its dependencies, deployment configuration, and exposed interfaces. Establish the application boundary and inventory routes, authentication flows, roles, privileged operations, secrets, databases, queues, file/object storage, admin tooling, and third-party integrations. Identify internet-facing assets and the data they process, especially credentials, personal data, and payment or tenant data.

Prioritize these checks:

- Authentication and session handling: verify strong password and MFA policies where appropriate, secure password hashing, safe token validation, expiration and revocation, secure cookie attributes, CSRF protection for cookie-authenticated state changes, and resistance to account enumeration and brute force.
- Authorization: test every object and function-level permission at the server, including tenant isolation, admin endpoints, background jobs, GraphQL resolvers, bulk operations, and alternate HTTP methods. Never rely on client-supplied role or ownership fields.
- Input and output handling: use allowlisted validation at trust boundaries; review SQL/NoSQL/LDAP/OS/template and expression injection; prevent path traversal, unsafe redirects, prototype pollution, request smuggling, and XSS. Encode output for its actual context.
- Node.js-specific risks: inspect `package-lock.json`/lockfile and transitive dependencies, remove unused packages, run audit tooling plus a review of reachable advisories, avoid unsafe deserialization and dynamic code execution, constrain child-process calls, and ensure errors do not expose stack traces, secrets, or internal topology.
- Data and secrets: remove credentials from source, images, logs, and build artifacts; use a secret manager and rotation; encrypt sensitive data in transit and at rest; minimize returned fields; redact logs; and verify backups, retention, and access controls.
- API and infrastructure hardening: enforce TLS, security headers, strict CORS, request size/time/rate limits, pagination bounds, safe compression settings, dependency and container patching, least-privilege service accounts, network segmentation, and secure production configuration. Confirm debug mode and development routes are disabled.
- Operational controls: centralize structured security logging without sensitive values, alert on authentication and authorization anomalies, preserve audit trails for privileged actions, define incident response and rollback procedures, and verify monitoring survives failure.

Use code review and automated SAST/SCA/secrets scanning, then exercise the running deployment with authenticated tests for each role and tenant. Include negative tests for missing, forged, expired, and cross-tenant credentials; fuzz validation boundaries; and run a DAST or penetration test against a staging environment representative of production. Treat scanner findings as leads, manually verify exploitability and reachability, and record evidence, affected asset, impact, likelihood, owner, and remediation deadline.

Do not approve release solely because tests pass or a dependency scanner is clean. Define release gates for no unresolved critical/high exploitable findings, rotated credentials, verified authorization coverage, safe production configuration, tested backups and incident response, and an explicit risk acceptance for anything remaining. Re-test fixes and perform a final configuration and secret scan on the exact artifact that will be deployed.
