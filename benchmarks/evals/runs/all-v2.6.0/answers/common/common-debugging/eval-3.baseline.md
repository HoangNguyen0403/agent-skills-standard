Use version-control and environment comparison to narrow the change systematically.

Start by confirm­ing the failure is real and define the comparison: exact input, expected versus actual result, runtime, dependency lockfile, configuration, database/data state, and deployment artifact. Check the working tree, recent commits, merge history, generated files, dependency updates, feature flags, environment-variable changes, migrations, and changes in upstream services. Commands such as `git status`, `git log --oneline --since=...`, `git diff <last-known-good>..HEAD`, and `git bisect` are useful, but inspect the actual patch rather than assuming the newest commit is responsible.

If the current revision fails and a known-good revision passes, use `git bisect` with a deterministic test or reproduction script. Mark revisions good or bad based on that same procedure, and stop when Git identifies a small suspect change. If the test is flaky, first measure and control timing, concurrency, network, clock, random seeds, caches, and test data; otherwise bisect results are unreliable.

For changes outside the repository, compare deployed artifact hashes, runtime and dependency versions, environment/config snapshots, schema versions, service health, permissions, and relevant production data. Review CI/CD logs to find when the artifact or configuration changed. Once a candidate change is found, reproduce the failure against it, write a regression test, fix the underlying contract, and verify the fix at unit, integration, and deployment levels. Record the causal change and evidence in the incident or commit so the result is auditable.
