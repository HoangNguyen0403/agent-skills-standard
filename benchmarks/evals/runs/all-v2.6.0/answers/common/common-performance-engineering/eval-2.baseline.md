A 10-second initial load for 5,000 table rows is usually a rendering and data-delivery problem, not something to solve by blindly optimizing every component. Profile the page first: measure time to receive the response, parsing and transformation time, React render/commit time, main-thread long tasks, memory use, and network payload size. Use the browser Performance panel and React Profiler with a production build.

The highest-impact UI change is virtualization/windowing. Render only the rows visible in the viewport, plus a small overscan buffer, using a well-tested library such as `react-window` or an equivalent. Ensure row keys are stable, avoid recreating large objects and callbacks on every render, and memoize row components only when profiling shows it prevents avoidable work. Keep expensive formatting and derived calculations out of each render; precompute or cache them where appropriate.

Reduce the initial data cost as well. Prefer server-side pagination, filtering, and sorting when the user does not need all 5,000 rows immediately. Fetch the first page quickly, load additional data on demand, and return only required fields. Compress responses and avoid redundant serialization or client-side transformation. If the full dataset must be available locally, consider chunked loading and deferred noncritical work, but preserve clear loading and error states.

After each change, test on representative hardware and data, and compare time to usable content, interaction responsiveness, total blocking time, memory, request size, and correctness. Add a regression performance budget—for example, a limit on initial payload, render duration, and long tasks—based on measured product requirements rather than an arbitrary target. Do not trade away accessibility, keyboard navigation, accurate row heights, or reliable sorting/filtering merely to improve the benchmark.
