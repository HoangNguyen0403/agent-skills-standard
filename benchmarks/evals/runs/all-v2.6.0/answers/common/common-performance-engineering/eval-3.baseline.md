Do not preemptively optimize every function. Without a measured problem, broad optimization creates risk: it increases code complexity, can introduce correctness and concurrency bugs, makes maintenance harder, and may spend effort on code that is not on a meaningful latency or resource path. Performance work should be guided by user-facing goals and evidence.

Start by defining service-level targets such as latency percentiles, throughput, startup time, memory, CPU, or battery use. Establish representative workloads and a repeatable baseline. Use profiling, tracing, database query plans, allocation or garbage-collection metrics, and production telemetry to identify the actual hot paths. Sampling profilers and end-to-end measurements are preferable to guessing from function names or isolated microbenchmarks.

Optimize the highest-impact bottleneck with the smallest safe change, then rerun the same workload to confirm a material improvement. Preserve behavior, document important tradeoffs, and add a benchmark or regression test when the path is critical. Recheck p50 and tail latency, resource consumption, scalability, and operational impact; an optimization that improves one microbenchmark but worsens overall throughput or readability may not be worthwhile.

Some low-cost preventive practices are appropriate: choose suitable algorithms and data structures, avoid known unbounded work and accidental N+1 I/O, set resource limits and timeouts, and design observable interfaces. But these are engineering defaults, not a mandate to rewrite all code. Keep a prioritized performance backlog tied to evidence, revisit it as workload and scale change, and optimize continuously where measurements show the expected benefit.
