Do not make Redis availability a dependency of every HTTP request. Separate queue/cache concerns from the request path, use bounded connection retries and timeouts, and configure the Redis client to fail fast when appropriate. A queue producer should either return an accepted result with durable retry/outbox semantics or report a controlled `503`; it should not leave requests hanging or throw an unhandled connection error.

Use a global exception filter to map known infrastructure errors to a safe `503 Service Unavailable`, with a request ID and useful logs, while keeping internal details out of the response. For cache reads, use a cache-aside fallback to the primary database when safe; never treat a cache miss or outage as an application failure. For workers, allow reconnects, backoff, and health/readiness reporting, and ensure liveness does not restart a process merely because an optional Redis dependency is temporarily unavailable. Add circuit breaking, metrics, and integration tests for Redis outage and recovery.
