# Diagnosing and fixing jank in a Compose `LazyColumn`

At 60 Hz a frame has about 16.7 ms, and high-refresh devices provide less time. First reproduce the problem in a release-like build with realistic data; debug builds and emulators can distort timing. Use a Macrobenchmark with `FrameTimingMetric` for repeatable scroll measurements, and use Android Studio's CPU/system trace plus Compose recomposition/layout tooling to find whether the time is spent in composition, measurement/layout, drawing, image decoding, or application work. A recomposition count alone is not a diagnosis: an inexpensive recomposition may be fine, while one expensive item can miss the frame budget.

Common causes and fixes include:

- Give items stable identity with `key`, and provide `contentType` when the list contains different item shapes. Without stable keys, insertions and removals can cause work and state to move across many rows.
- Keep item models stable and immutable. Prefer immutable collections and stable data passed to each item. Avoid passing a mutable list or frequently recreated wrapper object through the whole list. Use `@Immutable` or `@Stable` only when the type really satisfies the contract; annotations do not make an unstable or mutable design safe by themselves.
- Narrow state reads. Do not read rapidly changing state at the `LazyColumn` or screen level if only one row needs it. Use state hoisting with appropriately small scopes, `remember` expensive derived values, and use `derivedStateOf` when a frequently changing source should only invalidate UI when the derived result changes. Avoid creating new objects, modifiers, or lambdas on every recomposition when that work is measurable.
- Keep each row cheap. Move parsing, sorting, filtering, formatting, and other expensive computation out of item content and do it before rendering or on a background dispatcher. Avoid nested vertically scrolling containers, unbounded intrinsic measurement, unnecessary `SubcomposeLayout`, and custom drawing that performs heavy work per frame.
- Do not decode or transform large images on the main thread while scrolling. Use an image loader with lifecycle-aware requests, size images to the displayed bounds, and show a lightweight placeholder. Likewise, paginate very large data sets rather than composing or retaining every item at once.
- Make layout constraints predictable. Avoid item layouts whose height changes repeatedly as content arrives unless that behavior is intentional. Reserve image/aspect-ratio space, and avoid expensive animations or shadows on every row until profiling shows they are safe. Use `graphicsLayer` or other rendering changes only when they actually reduce the measured cost.

Check for accidental invalidation from a parent reading scroll state, such as directly using `firstVisibleItemIndex` in broad UI. If the value is only used to show a button or trigger a threshold, derive the boolean narrowly. Check also for work triggered by scroll callbacks, logging, analytics, or persistence; throttle or move it off the critical path.

A practical workflow is: capture a trace while performing the exact slow gesture; locate missed frames and the longest slices; isolate the responsible row or state read; make one targeted change; then rerun the same benchmark. Test cold and warm image caches, short and long lists, item insertion/removal, loading/error states, and a slower device. Do not solve jank by disabling useful content or animations without first measuring the cause; the goal is to keep composition, layout, and drawing within the frame budget under realistic conditions.
